# One Lantern — 구현 계획

작업명 `one_lantern` / 리포 `LampLight`
배포 대상: **웹 (Unity WebGL → GitHub Pages)**

이 문서는 기획 문서 세트 01~07을 구현 관점에서 재해석한 실행 계획이다.
기획서의 **게임플레이 수치는 채택**하고, **기술 사양(Web Audio 노드 그래프, Canvas 렌더링, localStorage)은 채택하지 않는다.**
기획서와 어긋나는 항목의 전체 목록과 근거는 [SPEC_DIVERGENCE.md](./SPEC_DIVERGENCE.md) 참조.

## 1. 기술 결정

### 1-1. Unity WebGL 유지 — Canvas 재작성 없음

리포에 이미 동작하는 자산이 있다.

| 영역 | 구현 상태 |
|---|---|
| 플레이어 | `PlayerController` — 걷기/달리기/살금, 스태미나, 발소리 훅 |
| 조명 | `Lamp` — URP `Light2D`, 원뿔 + 그림자 + 장애물 마스크 |
| 맵 | `MapData` 로더 · `MapCoord` 좌표계 · `MapPathfinder` · `MapObjectPlacer` · `SpawnSelector` |
| 적 | `EnemyBase` + `DefaultZombie` + `ActiveZombie`, 8방향 애니메이션 클립 |
| 프레임워크 | `Managers` (Resource / Pool / Scene / UI / Sound / Data / Input) |
| 테스트 | EditMode 6 + PlayMode 9 파일, 자동 플레이 봇(`PlayBot`) |
| CI | `game-ci/unity-test-runner`, 커버리지 + 아티팩트 업로드 |

기획서가 지정한 순수 Canvas + Web Audio 스택으로 재작성하면 위 전부를 버린다.
남은 일정 대비 손실이 압도적이므로 채택하지 않는다.

### 1-2. 빌드 · 배포

| 항목 | 값 |
|---|---|
| 압축 | **Gzip** |
| Decompression Fallback | **켬** |
| 배포 | GitHub Pages |

GitHub Pages는 `Content-Encoding` 헤더를 지정할 수 없어 Brotli 사전압축 서빙이 불가능하다.
Gzip + Fallback 조합이 로더 크기를 조금 키우는 대신 확실히 동작한다.

### 1-3. 오디오 아키텍처

Unity WebGL 오디오는 **볼륨만 제어 가능**하다. 이 제약이 설계를 결정한다.

| 기능 | WebGL | 결과 |
|---|---|---|
| AudioMixer 그룹 볼륨 | O | 버스 구조 가능 |
| 커스텀 rolloff 커브 / min·max distance / 팬 | O | 감쇠 직접 설계 가능 |
| `PlayScheduled` · `SetScheduledStartTime` | O | 리듬 정확도 확보 |
| pitch (양수) | O | 음높이 코딩 가능 |
| **AudioMixer 이펙트 · 저역통과 등 필터** | **X** | 벽 차폐 필터 불가 |
| **`OnAudioFilterRead`** | **X** | 런타임 절차 생성 불가 |

**(a) 절차 생성 → 사전 렌더 확정.**
`OnAudioFilterRead`가 없으므로 런타임 합성은 불가능하다.
아티스트 프로토타입(`playground/audio_test.html`)의 합성 코드를 `OfflineAudioContext`로 렌더해 파일로 굽는다.

**(b) 벽 차폐 → 사전 필터링 2종 + 볼륨 크로스페이드.**
음색 코딩은 기획서가 정의한 3개 생존 채널(리듬·음색·음높이) 중 하나라 포기할 수 없다.
필터를 못 쓰므로 클립을 두 벌 준비하고 볼륨 비율만 조절한다.

- 클립당 `_clear`(원본) / `_muffled`(저역통과 약 1.5kHz) 2종
- 벽 수 `n`을 Bresenham 레이캐스트로 100ms 주기 산출
- `muffledRatio = 1 - 0.45ⁿ` 로 두 소스의 볼륨만 블렌드
- 대상 9종(`artifact_ping` `exit_ping` `artifact_drone` `exit_hum` + 좀비 5종) × 2 = **18파일**

**(c) 리듬 → `dspTime` 스케줄링.**
이 게임은 재생 간격이 곧 거리 정보다. `Update()` 타이머로 돌리면 WebGL 프레임 드랍에 리듬이 흔들리고, 그 순간 게임이 플레이어에게 거짓 정보를 준다.
`AudioSettings.dspTime + period` 기준으로 한 틱 앞서 `PlayScheduled` 예약한다.

**(d) AudioMixer 에셋을 쓰지 않는다.**
WebGL에서 어차피 볼륨만 지원되므로, 믹서 에셋을 두는 이득이 없다.
코드 측 게인 그룹(`SoundBus`)으로 구현하면 EditMode 테스트가 가능하고 바이너리 에셋을 손으로 만들 필요도 없다.

```
Master
 ├ Guide    -6dB   유물 · 탈출구
 ├ Threat    0dB   좀비
 ├ Self     -3dB   발소리 · 호흡 · 상호작용
 ├ Ambient -30dB   룸톤
 └ UI       -9dB
```

달리기 덕킹(Guide·Threat −7dB, attack 30ms / release 250ms)은 볼륨 조작이라 제약 없이 가능하다.

### 1-4. 감쇠 커브를 평탄하게 설계한다

기존 프로토타입은 `inverse` rolloff(refDistance 1 / rolloff 1.6)를 써서 8타일에서 −37.6dBFS, 12타일에서 −42.8dBFS가 측정되었다. 노트북 내장 스피커로는 들리지 않는 수준이고, 모든 라운드가 8~12타일에서 시작하므로 첫 단서를 놓친다.

발상을 뒤집는다 — **거리는 리듬이 전달하므로 음량이 거리를 담을 필요가 없다.** 음량은 "존재 여부"만 담당한다.

| 거리 | 목표 감쇠 |
|---|---|
| 0~2타일 | 0 dB |
| 6타일 | −4 dB |
| 10타일 | −9 dB |
| 12타일 (반경) | −14 dB |
| 12타일 초과 | 무음 |

12타일 기준 기존 대비 약 29dB 이득.
마스터 컴프레서도 WebGL에서 못 쓰므로 클립을 사전 노멀라이즈해 내보낸다.

## 2. 맵 — 랜덤 생성 대신 고정 3장

기획서 03은 랜덤 생성을 "코어의 전제조건"으로 규정하지만 채택하지 않는다.

BSP 분할 + 루프 보정 + 하드 제약 10개 검증 + 30회 재시도 + 폴백까지가 최소 3~5일 작업이다.
같은 시간을 사운드 37종과 러너 구현에 쓰는 편이 결과물을 크게 개선한다.
랜덤 생성이 방어하려던 "2회차 암기" 문제는 짧은 시연 상황에서 발생하지 않는다.

현재 `Assets/Resources/Data/MapData.json` 한 장(60×40)을 세 장으로 재단한다.
60×40은 기획서 L3 최대치(34×22)보다 2.4배 넓어 등불 시간 안에 주파할 수 없다.

| | L1 | L2 | L3 |
|---|---|---|---|
| 목표 크기 | 20×14 | 26×17 | 32×20 |
| 유물 배치 / 필요 | 2 / 0 | 3 / 2 | 4 / 3 |
| 유물 소리 반경 | 12타일 | 9타일 | 7타일 |

생성기가 없으므로 하드 제약은 **EditMode 검증 테스트**로 대체한다. 두 개만 살린다.

| 제약 | 내용 | 이유 |
|---|---|---|
| **C6** | 유물 소리 반경이 겹치는 쌍 ≤ 1 | 두 리듬이 겹치면 거리 판별 불가 — 소리 게임의 생명줄 |
| **C10** | L1은 시작에서 5~9타일 내 유물 1개 | 시작 2초 내 첫 리듬음 보장 |

## 3. 실제 속도로 재계산한 파라미터

기획서의 시간 모델은 걷기 220px/s 가정 위에 있으나 코드는 4.0타일/s(=256px/s)다.
`MapCoord.TileToWorld`가 1 월드유닛 = 1 타일이므로 환산은 확정적이다.

같은 비율로 유효속도를 환산하면 3.27타일/s이고 모델은 다음과 같이 바뀐다.

```
est_sec = route_tiles × 1.5 / 3.27 + 8
```

| | 최적 동선 | 기획서 추정 | 재계산 추정 | 기획서 등불 | **채택 등불** |
|---|---|---|---|---|---|
| L1 | 28~42타일 | 25~35초 | **21~27초** | 75초 | **60초** |
| L2 | 45~62타일 | 40~50초 | **29~37초** | 95초 | **70초** |
| L3 | 65~88타일 | 52~65초 | **38~48초** | 115초 | **90초** |

채택값은 기획서가 의도한 여유율(2.1 / 1.9 / 1.8배)을 실제 속도에서 유지하는 수치다.

### 러너 재조정 (필수)

기획서 배율 1.9배를 실제 달리기 6.5타일/s에 적용하면 러너는 12.35타일/s다.
도주하는 플레이어와의 상대속도가 5.85타일/s이므로 경보(9타일)에서 즉사(3타일)까지 **1.03초**.
기획서가 의도한 2.4초는 물론이고 인간 반응시간과 거의 같아 불공정해진다.

| 항목 | 기획서 | **채택** | 결과 |
|---|---|---|---|
| 속도 배율 | 달리기 ×1.9 | **×1.5** (9.75타일/s) | 상대속도 3.25타일/s |
| 경보 반경 | 9타일 | **12타일** | 반응 구간 9타일 |
| 치명 반경 | 3타일 | 3타일 (유지) | |
| 반응 시간 | 의도 2.4초 / 실제 1.03초 | **약 2.8초** | 의도 회복 |

### 스태미나는 조정 불필요

코드(최대 5.0 / 소모 1.0per초)와 기획서(100 / 20per초)는 **달리기 지속시간이 5초로 동일**하다.
회복 속도만 코드가 빠르므로(6.25초 vs 10초) 그 값만 맞춘다. 스케일 재작업은 필요 없다.

## 4. 스코프

### 자른다

랜덤 생성기 · 튜토리얼 7단계(T0 인트로 + T1 소리 추적만 유지) · 은닉도 2단계 · 컨테이너(서랍·석관) · 돌멩이 · 인벤토리 UI · 등급 뱃지 이미지 4종(텍스트 대체)

### 유지한다

리듬 코딩 · 벽 차폐 블렌드 · 귀 기울이기 · 소리 링 · 좀비 3종 · **스태미나 게이지 삭제 + 호흡음 대체**

스태미나 게이지 삭제는 UI를 지우는 작업이라 비용이 음수이면서 기획서가 내세우는 차별점이다.
호흡음은 Self 버스에 얹으면 마스킹이 자동으로 발생한다.

### OilCanister 처리

이미 구현되어 있고 기획서에는 없다. 삭제하지 않는다.
**L1·L2에 0개, L3에만 1개를 위험한 위치에 배치**한다.
코드 변경 없이 배치 데이터만으로, 설계와 어긋나던 시스템이 리스크·리워드 선택지가 된다.

## 5. 마일스톤 — 리스크가 큰 순서

### M0 · 배포 경로 관통 (최우선)

검은 화면 + 점 하나 + ping 하나짜리 Unity WebGL 빌드를 GitHub Pages에 올리고 **실제 노트북 내장 스피커로** 유물 도달 시간을 측정한다. 합격선 20초, 40초 초과 시 반경 확대 또는 소리 링 강화.

이 순서인 이유: 아티스트 프로토타입은 *개념*을 검증했을 뿐 *전달 경로*를 검증하지 않았다.
Unity WebGL 오디오 언락, rolloff 커브, gzip 로딩, 실기기 스피커 — 게임이 죽을 수 있는 지점이 전부 여기 남아 있다. 마지막에 확인하면 손쓸 시간이 없다.

이 테스트 하나로 리듬 계수 0.30, 반경 12/9/7, 소리 링 필요성이 동시에 확정된다.

### M1 · 오디오 코어

`SoundBus` 5버스 · `dspTime` 기반 `PingScheduler` · 차폐 2종 블렌드 + Bresenham 레이캐스트 · 오디오 언락(Title 씬) · 12보이스 풀링(`PoolManager` 재사용)

사운드는 ★★★ 20종 우선. `artifact_ping` / `exit_ping` / `runner_alert`는 사전 렌더, 나머지는 CC0 라이브러리.

### M2 · 위협

러너 신규 구현(×1.5 / 12타일) · `ActiveZombie` 추격 로직 재검토 · `EnemyState.Stunned` 정리

### M3 · 레벨

맵 3장 재단 · 레벨 진행 및 재시작 · 점수와 등급 · 등불 60/70/90 적용 · C6·C10 검증 테스트

### M4 · 마감

귀 기울이기 · 소리 링 · 축약 튜토리얼 · 호흡음 마스킹 · 로딩 화면

| 등불 | 60초 | 70초 | 90초 |
| 좀비 | 느린것 1 | 느린것 2 + 도는것 1 | 느린것 2 + 도는것 2 + 러너 1 |
| 등급 컷 S/A/B | 1800/1300/900 | 2900/2200/1600 | 4200/3300/2500 |

L1은 필요 유물이 0개라 탈출구가 처음부터 열려 있고, 유물 2개는 점수용 유혹으로 남는다. 시작 지점 7~9타일에 각성 좀비 1마리를 배치해 02 §6-2의 첫 10초 후킹을 보장한다. 3회 연속 실패 시 등불 +20%.

점수는 `ScoreRules.Total` — 기본 500×레벨 + 유물 300 + 잔여 등불×10 + 무소음 400 + 회피 250. 무소음 보너스가 시간 보너스보다 크도록 테스트로 고정했다.

### M5 · 맵 3장 · 은닉도 · 튜토리얼 · 등급

**맵 3장 분리** — BSP 베이커(오프라인)로 L1 20×14 / L2 26×17 / L3 32×20을 생성해 `Resources/Data/map_l1~l3.json`에 굽는다. 방 4·6·8개, 보행 비율 0.44~0.49, 복도 폭 2타일.
씬에 사전 페인트된 타일맵으로는 레벨 전환이 불가능하므로 **런타임 페인터**(`MapTilemapRenderer` + `MapPalette`)를 추가했고 `DataManager.LoadLevelMap`이 레벨별로 로드한다.
하드 제약 C1·C2·C5·C6·C10과 스폰 조건은 `MapBakeTests`가 검증한다.

**은닉도 0/1/2** (`ConcealmentRules`) — 소리 반경 ×1.0/0.75/0.55, 획득 홀드 0/1.0/1.5초, 획득 소음 6/7/10타일, 점수 가중치 1.0/1.3/1.6.
은닉도 2가 곧 컨테이너(석관·서랍)이므로 별도 오브젝트 없이 개방 메커닉이 성립한다. `IInteractable`에 홀드를 추가하고 진행률을 HUD에 표시한다.

**돌멩이** (`StoneThrower` + `NoiseLure`) — L3에서 2개, 좌클릭 투척, 최대 8타일. 착지 지점에 소음원이 생겨 좀비 3종이 플레이어가 아닌 그쪽으로 향한다. 세 좀비의 청취 로직을 `EnemyBase.TryHearNoise`로 통합했다.

**튜토리얼** (`TutorialController`) — 인트로 4줄 → 등불 점화 → 페이드인 → "들리는 쪽으로 가라". noisy 바닥 진입 시 "조용히 걸어라", 첫 귀 기울이기에 "덜 보면 더 들린다". `PlayerPrefs`로 1회만, 배치 모드에서는 건너뛴다.

**등급 뱃지** (`RankBadge`) — PNG 에셋 대신 런타임 텍스처로 생성(S 호박 / A 청록 / B 회청 / C 회색). 임포트 설정이 필요 없고 결과 팝업에 직접 붙는다.

### M6 · 런타임 생성 · 튜토리얼 완성 · WebGL 오디오 가드

**런타임 랜덤 맵 생성** (`MapGenerator`) — 기획서 03의 BSP+루프 보정을 C#으로 이식했다. 시드 PRNG, 최대 30회 재시도, 실패 시 베이크된 고정 맵으로 폴백한다.
한 레이아웃당 앵커 배치를 48회까지 시도하고 유물은 **최원점(farthest-point) 선택**으로 뽑는다. 무작위 선택만으로는 C6(소리 반경 겹침 ≤1)을 30회 안에 만족시키지 못해 생성이 전부 실패했다.
`MapGeneratorTests`가 시드 결정성, 레벨별 크기, C1·C2·C3·C5·C6·C10, 복도 폭 2타일을 레벨×시드 조합으로 검증한다.

**튜토리얼 전체 단계** — 인트로 4줄 → 등불 점화 → 페이드인 이후, 실제 게임 이벤트에 힌트를 묶었다.
noisy 바닥 진입("조용히 걸어라") · 첫 귀 기울이기("덜 보면 더 들린다") · 좀비 추격 시작("들켰다 — 도망쳐라") · 첫 유물 획득("정보에는 대가가 있다") · 탈출구 개방("소리를 따라 나가라"). L1에서만, `PlayerPrefs`로 1회.

**WebGL 오디오 로드 가드** — 브라우저 실입력 검증 중 `Trying to get length of sound which is not loaded yet`가 5회 찍혔다.
WebGL은 오디오 클립을 비동기로 디코딩하는데 씬 로드 직후 루프 사운드가 곧바로 재생을 시도한 탓이다. `AudioTuning.IsReady`(`loadState == Loaded`) 가드를 모든 재생 경로에 넣어 해소했다.

### 브라우저 실입력 검증

앞서 합성 `dispatchEvent`가 Unity에 전달되지 않아 Title 부팅까지만 확인했는데, **CDP 경유 실입력**(Playwright `page.mouse` / `page.keyboard`)은 정상 전달된다.

| 동작 | 결과 |
|---|---|
| 시작 버튼 클릭 | 씬 전환 확인 (`Unloading 5 Unused Serialized files`) |
| WASD 이동 | 에러 0 |
| Shift 달리기 | 에러 0 |
| 우클릭 귀 기울이기 | 에러 0 |
| 콘솔 에러 | **0** |

남은 경고 2종:

| 경고 | 판단 |
|---|---|
| `WebGL: INVALID_ENUM: getInternalformatParameter` ×6 | URP의 포맷 탐색. 모든 Unity WebGL 빌드에 나온다 |
| `The AudioContext was not allowed to start` ×57 | **헤드리스 크롬의 자동재생 정책으로 보이나 확정 못 했다.** Unity 6은 `WEBAudio` 핸들을 전역 노출하지 않아 컨텍스트 상태를 페이지에서 조회할 수 없다. 실제 브라우저에서 소리가 나는지 확인이 필요하다 |
